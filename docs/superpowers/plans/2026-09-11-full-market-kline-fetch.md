## 1. 背景

### 1.1 现状架构（已核实）

- **K线主源是腾讯财经**，不是同花顺：`web.ifzq.gtimg.cn/appstock/app/fqkline/get`（免费、无登录、单次≤500条≈700自然日、3域名自动failover、qfq/hfq/不复权均支持）。iFinD（同花顺）目前**只用于财报PIT指标**（THS_BD，批量25只/次），东财是财报兜底。
- **存储方式**：`artifacts/.cache/` 下**按股票×类型一个JSON文件**，共7类后缀：
  | 后缀 | 口径 | 用途 |
  |---|---|---|
  | `_kline` | 10年 qfq | scan_watchlist（旧默认） |
  | `_klineh` | 10年 hfq | 报告链路（收益/MA口径） |
  | `_kline20` / `_kline20h` | 20年 qfq/hfq | 回测（跨牛熊） |
  | `_raw_kline` / `_raw_kline20` | 10年/20年 不复权 | 历史PE/PB（真实价） |
  | `_index_kline` | 上证指数 | 牛熊分段 |
  当前46只watchlist ≈ 283个文件、56MB。每文件含 data + pe/pb/price/name/qt_date/volume 元数据。
- **统一入口**：`kline_cache.get_kline / get_kline_raw / load_cache / save_cache`（全量+增量+除权自动全量重拉）。已核实**所有下游都经此API读数**（build_report / scan_watchlist / run_backtest / market_regimes），报告HTML是自包含的——K线数据在构建时内嵌进HTML，**不直接读缓存文件**。
- **iFinD账号单点登录**：多进程登录互踢（err=-1010），`ths_fetcher._bd_retry` 已实现被踢自动重登。

### 1.2 现在的代码能不能直接全市场抓？

**单只能抓，批量不行**，缺三块：

1. **没有获取股票列表的代码**——watchlist.txt 是手工维护的46只。
2. **没有批量编排**——无任务账本、无断点续传、无失败清单重试、无并行。串行跑全市场 ≈ 5400只 × 44次调用 ≈ 24万次API调用，单线程15~20小时，且中途断了只能重来。
3. **JSON存储撑不住全市场**——5400只 × 6类 ≈ 3.2万个小文件、约8~10GB；每日增量是整文件重写；回测要一次读几千个JSON。

## 4. 关键决策

### D1 K线主源维持腾讯，iFinD退居列表+对账（重要，与你"优先同花顺"的偏好相左，理由如下）

- 现有K线链路（含除权检测重拉、域名failover）全部构建在腾讯接口上，已在46只上验证。
- iFinD的K线接口（THS_DateSerial/THS_HistoryQuote）**本仓库从未用过**：全市场20年日K约2600万行，账号有每日数据量配额，超配额任务中断风险高；且单点登录强制串行，速度上不去。
- 腾讯无需登录、可多线程、无显式配额（隐性限频用间隔+jitter对付）。量化对比：
  - 腾讯：只抓20年两类 × 11次/只 ≈ **12万次**（10年两类由切片推导，见D6），**3线程+0.3~0.5s jitter ≈ 5.5~6小时（8小时预算内）**；
  - iFinD同量数据：单进程串行 + 配额未知，**不可控**。
- iFinD的定位：①拉股票列表（一次调用）；②抽样对账源（20只）；③财报（既有职责）。

### D2 列表源：iFinD板块/指数成分为主，东财clist兜底

- iFinD全A成分的具体指标名需先小样本验证（从未在本仓库使用）；东财 `push2.eastmoney.com/api/qt/clist/get` 是公开稳定接口（100只/页 × ~54页，无需登录，本仓库已有东财兜底先例）。
- 两源取并集做diff，不一致项人工复核；过滤只留沪深A股（6/0/3开头）。
- **北交所今晚排除**：`get_kline` 的交易所推断只认 `6→sh` 其余→`sz`，北交所（43/83/87/920开头）会被误判为sz；腾讯bj前缀支持也未验证。列入后续待办。

### D3 存储换SQLite单文件（stdlib自带，零新依赖）

- 表1 `kline(type, code, date, open, high, close, low, volume, PK(type,code,date))`，type即7类后缀；
- 表2 `meta(type, code, pe, pb, price, name, qt_date, volume, updated)`；
- 表3 `stock_basic(code PK, name, market, list_date, status, excluded, excluded_reason, updated)`——全A基础信息只在列表阶段拉一次入库，夜间增量与后续任务直接读表，避免重复获取；
- 表4 `fetch_ledger(code, ktype, status, rows, last_date, attempts, updated_at)`——断点续传账本（见Step 3）；
- 对比：~7000万行 ≈ 3~4GB单文件（JSON为8~10GB、3.2万文件）；日增量=每股一个事务DELETE+INSERT，秒级；回测全量加载=一次SELECT；
- 备选DuckDB/parquet：分析扫描更快但增量写不自然且要装新依赖，若回测加载实测慢再升级；
- **兼容方式**：`load_cache/save_cache` 改为读写DB（返回dict结构完全不变），JSON保留只读兜底一周后清理。

### D4 停抓10年qfq（`_kline`），scan_watchlist切hfq

qfq与hfq只差一个乘性常数，比率类因子（MA偏离、量比、波动率）数学不变。切换前用46只watchlist做新旧分数diff回归验证；验证不过则保留qfq类一起抓（多花约1/4调用量）。

### D5 报告HTML：不需要任何改动

报告是自包含HTML，K线经 `get_kline` 在构建时内嵌。存储替换完全收在 `kline_cache.py` 内部，对外函数签名与返回结构不变，下游（build_report/scan_watchlist/run_backtest/market_regimes/summary_report）**零适配**。唯一要新写的是：全市场批量编排脚本、SQLite后端、存量迁移工具。

### D6 抓取口径压缩：只抓20年两类，10年/qfq切片推导（2026-09-12 修订）

hfq 以上市初为基准、raw 为客观价，两者都不随请求窗口变化——**10年hfq/raw 就是 20年序列的尾部切片**，qfq 可由 `qfq_t = hfq_t × raw_T/hfq_T` 推导（T=最新日；比率类因子对常数基准不敏感，PE/PB 用 raw）。因此每只只抓 20年hfq + 20年raw 两类：

- 调用量从 ~40次/只（4类口径+3年分块）降到 **22次/只**（700自然日线性窗口 × 2类），全市场 ~12万次；
- 每日增量同步减半：20y两类各1次增量（2次/只/天），10年缓存重新切片、qfq重新推导，0调用；
- 除权检测只在20年序列上跑一次（原来4类各检一遍）；
- 10年缓存写入时按日期截取最近10年窗口，与报告链路10年分位窗口口径一致；
- **执行补充（2026-09-12）**：东财列表混入约180个2006年前退市遗留代码（PT金田A等，窗口内无数据）→ 证据式排除（空响应→excluded=1）；列表抓取触发东财反爬 → push2delay 延时域名 + 浏览器头轮换；腾讯主域连续10万+调用后出现整域501，`_fetch_with_retry` 第三域名自动接管。

### D7 重要发现：腾讯 hfqday 是"乘法+加法混合"复权（现金分红口径），非纯乘法后复权（2026-09-12 执行期发现）

- **证据**：①涨跌停日收益被系统性压缩：000539 2025-05-28 raw +10.11%（腾讯/东财两源一致的涨停）而 hfq 仅 +5.93%；000539/601857 在 2024-26 年 raw |收益|>9% 的交易日，hfq 收益中位 ~6.3% vs raw ~10.0%。②hfq 与 raw 呈**分段仿射关系 hfq = a + b×raw**（000539 2024-26 逐日斜率恒定 8.80~8.85，仅事件日跳变；601857 的 hfq/raw 比值随 raw 上升而下降 1.70→1.47，纯乘法不可能）。③与 iFinD 文档"现金分红复权涉及加减与乘除迭代运算"互证。
- **影响**：hfq 日收益 ≠ 真实总收益（高累计调整额股票的大涨日被压缩，绝对收益偏保守）；原审计"hfq 收益率与 qfq 数学一致"的表述不成立（两者同为混合口径）。全系统一直构建于此口径且当晚数据与历史缓存逐行一致——**已验证结论内部自洽性不受影响**；8只重组老股在极端事件后出现负值价格（180行/0.15%）。
- **后续决策项**：是否切换真·乘法后复权（raw × 交易所除权事件因子自建，或引入 iFinD 分红再投因子）——口径切换会改变全部收益/MA 因子值，**必须重跑参数网格验证**后方可采纳。

### D8 复权口径修复：表驱动重建 kline20r + A/B 验证（2026-09-12 执行）

**修复方法**（`scripts/build_total_return.py`，保真优先）：
- 非事件日 `T_ret = raw 收益`（构造性保真，不引入估计误差）；表内事件日 `T_ret = ((1+送转比例)×收盘 + 每股派息)/前收盘 − 1`（分红按除权日收盘再投）；表外检出事件日（配股等，东财分红送转表不含配股）`T_ret = 0`（配股对价公允、送转不创造价值）。
- 表外事件检出判据不需估计复权因子：raw 下跌≥3% 且 hfq 跌幅不足其一半（普通日 hfq 斜率 b≥1 必然 |Δhfq|≥|Δraw|）。
- 新口径 ktype = `kline20r`（`kline_store` 后缀映射 `_kline20r`）；切换开关 `VALVE_HFQ_KTYPE=kline20r`（kline_cache 只读服务、缺失回退默认，绝不去腾讯抓替代序列）。
- 事件表预热：`scripts/warmup_bonus_events.py`（东财限速约 0.5/s，全市场 5348 只约 2-3 小时，账本断点续传）。

**验证（46只 watchlist）**：重建收益 vs raw 收益（非事件日偏离>0.5%）46/46 通过（构造性 100% 保真）；东财事件金额与数据反解金额 0 处不吻合；恒正、无异常跳变。

**A/B 影响测试（20年回测 + 参数网格）**：策略年化 11.73%→13.40%（+1.67pp）；相对百分位策略超额 +2.88→+5.91（翻倍）；池化IC(250日) 0.1203→0.1266；分层更单调（3.78/5.01/4.65% → 4.10/5.25/5.33%）；最大回撤 −58.6%→−60.7%（真收益基数更高所致）；**参数网格推荐「买95分位/卖10分位」两口径完全一致**（新口径下排名更优 rank_avg=1.0）。

**建议**：采纳新口径（参数结论经A/B验证不变、指标全面改善）；切换前待办：全市场重建与校验、46只之外的保真度抽查、配股/表缺失事件清单确认。旧口径 `kline20h` 保留作对照与回退。报告见 `复权口径问题分析报告.html`。
- 腾讯接口实测（2026-09-12）：**无复权因子字段**（行=6列OHLCV），且一次请求只返回所请求口径的数组——"一个价格+因子"模式在腾讯不可行，两口径各拉一遍是唯一解；腾讯自家 qfq 与 hfq 链在除权事件上有 ~0.2% 级差异（比率类因子不受影响）。`factor_t = hfq_t/raw_t` 可免费反推作校验。
- akshare 因子路径核实（2026-09-12）：akshare 无独立因子接口，唯一路径是新浪系 `stock_zh_a_daily(adjust='hfq-factor')`（东财/腾讯来源均不支持因子）。**决策：不采用**——省 ~11次/只（22→12）但预算本已够用，换来的是跨源基准错位（新浪因子比率 vs 腾讯价格链事件级bp级偏差）、新浪限流新风险面、akshare 重依赖、增量维护多一层因子状态机。定位：①抽样校验源（对比 factor_t=hfq/raw 与新浪 hfq_factor）；②腾讯接口失效时的 Plan B。
