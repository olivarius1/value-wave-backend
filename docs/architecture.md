### 1.2 生产化差距（诚实评估）

**不是生产级系统**。缺的不是能力，是"组织"：

1. **kline20r 未接入每日增量**——目前是一次性批处理产物；每日增量只更新 kline20h/raw_kline20，新口径会逐渐过期（P0）
2. **无调度**——所有流程靠手工触发或一次性后台命令；无定时任务、无依赖编排（P0）
3. **无监控告警**——账本有失败记录但没人看；校验结果只落 JSON 不推送（P1）
4. **数据源逻辑分散**——限速/重试/缓存各脚本各写一份，改一处要同步多处（P1）
5. **口径未显式化**——报告/回测输出没有标注"使用哪个复权口径"，A/B 期间容易混淆（P1）
6. 无测试、无 runbook（P2）

## 2. 目标架构

单机、单人、SQLite——**不做过度工程**（无消息队列、无微服务、无数据库服务器）。

```
┌─────────────────────────────────────────────────────────┐
│ 入口层   cli.py（统一命令）        cron入口（每日流水线）    │
├─────────────────────────────────────────────────────────┤
│ 编排层   pipeline.py —— 任务依赖图 + 统一账本 + 失败重试    │
│          （项目内约200行Python；调度用系统crontab；        │
│           不是 Jenkins/Airflow 这类外部系统，见 §2.1）      │
│          全量初始化 │ 每日增量 │ 口径重建 │ 校验报告        │
├─────────────────────────────────────────────────────────┤
│ 数据源层 datasource/（本层是本次重构的核心新增）            │
│   tencent.py   kline(全量/增量), 限速+failover            │
│   eastmoney.py clist, 分红送转, 财务兜底, 限速             │
│   ifind.py     PIT财报（单进程约束内聚在此）               │
│   共同基类: 限速器/重试/退避/缓存包装                        │
├─────────────────────────────────────────────────────────┤
│ 存储层   kline_store(SQLite WAL, 统一账本)                 │
│          financial cache(30天)                            │
├─────────────────────────────────────────────────────────┤
│ 计算层   build_total_return / scoring_engine              │
│          backtest_engine / market_regimes（纯函数，无IO）   │
├─────────────────────────────────────────────────────────┤
│ 输出层   reports(HHTML/JSON) + 校验摘要 + 口径标注           │
└─────────────────────────────────────────────────────────┘
```

**设计原则**
1. **增量优先**：一切批处理必须支持增量续跑（K线已有、事件按缓存过期、重建按尾部续接）
2. **账本统一**：kline/bonus/rebuild 三本账并入 kline_store，一处查询
3. **数据源内聚**：每个外部源一个适配模块，限速/退避/缓存只写一遍
4. **口径显式**：所有产出标注复权口径；切换 = 改一处配置
5. **校验即阶段**：流水线每阶段后置校验，不过不进下一阶段
6. **计算无IO**：引擎函数只吃内存数据（现状已满足，保持）

### 2.1 编排层的具体形态（不是 Jenkins）

Jenkins 是软件构建/CI-CD 工具（Java Web 服务、插件体系、需运维），数据流水线的"任务"是 Python 函数 + 账本，用不到它的任何能力，反而引入运维负担。本项目编排层 = **项目内一个 pipeline.py（约200行）+ 系统 crontab**：

```python
# pipeline.py 形态示意
TASKS = {  # name: (函数, 依赖, 校验器)
  'kline_incr':   (stages.kline_increment,  [],            check.kline_fresh),
  'events_incr':  (stages.events_refresh,   [],            None),
  'kline20r_tail':(stages.total_return_tail,['kline_incr'], check.tr_fidelity),
  'validate':     (stages.validate_all,     ['kline20r_tail'], None),
  'report':       (stages.daily_report,     ['validate'],  None),
}
# run('daily') 按依赖序执行；每任务自带账本断点续传；校验器不过 → 终止+告警钩子
```

调度 = `crontab: 30 18 * * 1-5  python cli.py daily`（一行）。升级路径（若真有需要）：cron+pipeline.py → Prefect/Dagster（Python 原生数据编排，轻量）——Jenkins 始终不在候选之列。

## 3. 数据流水线（回答"以后有分红送转怎么办"）

### 3.1 全量初始化（已完成，2026-09-12）

```
列表(clist) → K线全量(腾讯,20y×2口径) → 事件表预热(东财) → 口径重建(kline20r) → 校验
```

### 3.2 每日增量流水线（核心设计，回答问题1）

**分红送转是"事件流"，不是"重算流"**。每只股票每年只有1~2次事件，处理方式是**尾部续接**而非全量重跑：

```
每日 18:30（收盘后）cron → pipeline daily:
  1. kline 增量        腾讯 2调用/只（20h/raw 各一次增量）→ 账本
  2. 事件表刷新        仅30天缓存过期的股票（≈180调用/天，滚动摊销）
  3. kline20r 尾部续接  对每只新增K线的股票（本地计算，0网络）:
                        当日在事件表 → 按事件公式接收益
                        不在       → ret = raw收益（构造性保真）
                        当日检出"raw机械下跌而hfq抹平"且表内无记录
                                   → 记入"待核对事件"清单（次日复核）
  4. 校验             行数/last_date/恒正/保真度抽检 → 失败告警
  5. 汇总输出          更新 summary + 状态页
```

关键点：
- **事件表天然滞后**（分红要等实施公告），因此续接时"当日在事件表"通常来不及——正确做法是**除息日当天 raw 会机械下跌**，此时若事件表还没有该记录，先按普通日接（错误！会留一个假跌）。所以第3步的续接必须**回看窗口**：发现 raw 单日异常下跌（≤-1.5%）且当日无表内事件的，**挂起该股最后1日不续接**，等事件表下轮刷新补上事件后续接。这是唯一需要"延迟确认"的地方，设计里显式化。
- 事件表预热保持每周末全量刷新一次（兜底），每日只增量刷新过期缓存。

### 3.3 口径切换（一次性动作）

A/B 已验证参数结论不变（见复权口径分析报告）。切换 = 报告/回测链路改读 `kline20r`（配置项），`kline20h` 保留回退。

## 5. 路线图

**P0（本周，让系统"活"起来）**
1. `daily` 流水线：kline增量 + 事件表增量刷新 + kline20r尾部续接（含回看挂起逻辑）+ 校验（代码量小：复用现有函数）
2. cron 落地（每日18:30 + 周末全量刷新）
3. 口径切换到 kline20r（全市场重建完成并校验通过后）

**P1（本月，让系统"可托付"）**
4. 失败/校验告警推送（企业微信/邮件，账本失败数>阈值即报）
5. datasource 适配层重构（限速/退避/缓存收敛）
6. 状态页（一个自包含HTML：各表新鲜度/账本/最近校验）

**P2（按需）**
7. 回测宇宙扩展（全市场财报PIT预热——独立战役，iFinD配额先验证）
8. 北交所支持、退市股历史成分
9. 单元测试（优先：build_total_return 的链式公式与事件检出）

**明确不做**：消息队列、微服务、服务器数据库、多用户。单机 SQLite + cron 是当前规模的最优解。
